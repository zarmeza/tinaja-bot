### 2026-10-08, local LLM chat

- **Benchmark before building.** No bot code until Vulkan is measured. Every
  design question below -- streaming vs one-shot, model size -- depends on
  whether this GPU does 25 tok/s or 12, and guessing costs a rewrite.
- **Model is Qwen2.5-3B-Instruct Q4_K_M (~2GB)**, with 1.5B downloaded
  alongside purely for comparison. 4GB VRAM is the real ceiling and 3B fits
  with room for KV cache.
- **`llama-server` runs on the host**, not in a container. The bot container
  cannot reach the host localhost; alternatives are a sibling compose service
  or `extra_hosts`. A sibling service is the most portable and matches how
  `browser` already works here, but needs a llama.cpp image with Vulkan and
  upstream ships no Dockerfile. Host is less work and easier to curl when
  debugging.
- **Docker networking, for the record** -- this is the part that is easy to get
  wrong: a container has its own network namespace, so `localhost` inside it is
  the container, not the machine. Three ways out: (1) sibling service in
  compose, reachable by service name, which is what `scrappy` already does
  with `browser`; (2) `extra_hosts: host.docker.internal` plus a host process;
  (3) `network_mode: host`, Linux only, so rejected as it breaks Mac and
  Windows.
- **`!chat` rather than mention-triggered**, pending the open questions below.
  The existing bot is strictly `-`-prefixed, one command per file, so a
  mention-triggered feature needs a message listener and is a structural change
  rather than one more file in `commands/`.


### 2026-10-08, chat design decided

- **Mention-triggered takes priority**, with `!chat` still supported
  afterwards if time allows. The instinct was to keep it prefix-only because
  that fits the existing architecture, but a Discord bot that ignores you
  unless you remember a bang is a worse experience, and dropping the prefix
  for now simplifies the first slice: no command file, no dynamic loader, no
  module-name camelization to fit through.
- **Memory is per-channel, in-memory, last N turns.** N is not fixed yet and
  should come out of the benchmark -- a larger context is more prompt to
  re-read per request, and at any plausible tok/s that cost is felt.
  Deliberately not persisted: that is a data-shape decision, not a feature.
- **One thread per conversation.** Context stays visible to everyone instead
  of scrolling away, at the cost of one extra Discord API call.
- **Spanish, TINAJA flavour, with a system prompt.** Chosen over raw
  completion because output quality moves more on this than model size does.
- **Casual-chat scope, for now.** Explicitly a starting position, not a
  judgement that hallucination is acceptable forever: 3B models invent
  confident nonsense on anything needing real knowledge, and this is an
  engineering community. Revisit if the chat ever becomes study help, at
  which point a refusal-flavoured system prompt is the cheap mitigation and
  retrieval is the real one.


### 2026-10-08, CPU baseline measured

Measured with `llama-bench`, Qwen2.5-3B-Instruct Q4_K_M, 8 threads, build
`c811cb8f0`:

| test | result |
|---|---|
| generation, tg64 | **5.88 +/- 2.21 t/s** |
| prompt processing, pp512 | **31.15 +/- 0.18 t/s** |

This is the number the Vulkan build has to beat, and it is well below the 12
t/s the user remembers from Windows -- which is consistent with that 12 having
been GPU-measured on a heavier model. It is also why the benchmark came first:
on this CPU a 200-token reply is ~34 seconds, which would have ruled out
streaming outright.

Prompt processing is the surprising half. At 31 t/s, a 512-token prompt costs
~16 seconds, and multi-turn memory re-sends the whole history every request.
Four turns of conversation plus a system prompt is roughly 700 tokens, so
~22 seconds of pure overhead before a single token is generated. **Turn count
in memory is therefore expensive in a way that is not obvious from tok/s
alone** -- this is the measurement the memory decision needed, and it argues
for a small cap (4-6) rather than the 8 first considered.

Model download verified: 2104932768 bytes, GGUF magic `47 47 55 46`. Note the
download started from a 1108-byte redirect body, so checking the magic bytes
rather than trusting curl exit status is worth doing on any future download.


### 2026-10-08, Vulkan benchmark

Measured on the RX 560D, `llama-bench`, build `c811cb8f0`, `RADV POLARIS11`,
4096 MiB, confirmed as real hardware rather than llvmpipe:

| test | CPU | Vulkan | speedup |
|---|---|---|---|
| generation, tg64 | 5.88 t/s | **28.02 t/s** | **4.8x** |
| prompt processing, pp512 | 31.15 t/s | **173.52 t/s** | **5.6x** |

This clears the ~25 t/s threshold set before any code was written, so the two
deferred decisions resolve:

- **Streaming is viable.** At 28 t/s, a 200-token reply is ~7 seconds, and
  editing one Discord message per token is comfortably within rate limits.
  Worth doing rather than leaving deferred.
- **The memory cost is much smaller than the CPU baseline implied.** Prompt
  processing at 173 t/s means a 700-token four-turn history costs ~4 seconds
  rather than ~22, so the 4-6 turn cap can go back up toward 8-10 without the
  overhead dominating.

The 12 t/s originally remembered from Windows now makes sense as a heavier
model on this same GPU. Nothing here contradicts it; it just was not the same
configuration.

### 2026-10-08, local LLM chat

**ROCm is installed and broken on this machine.** `rocminfo` reports
`HSA exception: Agent creation failed`. The card is Baffin/GCN4, which
predates ROCm supported range, so this is permanent, not a misconfiguration.
Do not spend time on it. RADV (Vulkan) is the working path.

**An earlier plan assumed CPU-only inference and was wrong.** The 12 tok/s
figure remembered from Windows was measured on the GPU, not the CPU. That
inverted the whole sizing analysis: a 7B partially offloaded plausibly
produced 12 tok/s, which means a fully-resident 3B should land meaningfully
faster. The CPU-only framing -- 4 cores, 8 threads, pick the smallest model
possible -- was retracted.

**~~Reading `/dev/dri/renderD128` will hang or fail, and Vulkan will silently
fall back to software.~~** **This warning was wrong, and it was repeated twice
before being checked.** It was inferred from the mode bits alone:

    /dev/dri/renderD128 -> crw-rw---- root:render
    id -Gn -> zarmeza adm cdrom sudo dip plugdev users lpadmin lxd docker

The `+` on the `ls -l` output was the tell. `getfacl` shows udev had already
granted a per-user ACL:

    user:zarmeza:rw-

so the nodes were readable before `usermod` ran, and would have been readable
without it. The predicted llvmpipe fallback never applied here, and the
`usermod -aG video,render` step was harmless but unnecessary.

The generalisable version: **`ls -l` mode bits are not the whole story when the
output has a `+`.** Check `getfacl` before concluding a device is inaccessible.
Asserting a specific failure mode twice from indirect evidence was the actual
error, and it cost two round trips of confident-sounding wrong advice.

**Building the Vulkan backend needs four packages, not the two the docs imply.**
`glslc` and `libvulkan-dev` clear `find_package(Vulkan)`, and then the configure
stops dead on a third:

    ggml/src/ggml-vulkan/CMakeLists.txt:14 -> find_package(SPIRV-Headers CONFIG REQUIRED)

That is an unconditional find rather than an optional component, so
`-DGGML_VULKAN=ON` cannot complete without `spirv-headers`. The failure is a
CMake configure error rather than a compile error, which reads as a build-system
problem rather than a missing dependency.

`glslangValidator` is still absent and is fine -- CMake lists it under *missing
components*, not errors, so `glslc` alone is sufficient. Worth knowing before
spending time installing it.


### 2026-10-08, Vulkan works

**Setup needed four packages, not two.** `glslc` and `libvulkan-dev` get the
build past `find_package(Vulkan)`; then `ggml-vulkan/CMakeLists.txt:14` hits
`find_package(SPIRV-Headers CONFIG REQUIRED)`, which is *not* vendored and
needs `spirv-headers`. That is an unconditional find rather than an optional
component, so the configure cannot complete without it.
`glslangValidator` remains absent and is fine -- CMake reports it as a missing
component rather than an error.

**The `video`/`render` group change was unnecessary, and two earlier warnings
about it were wrong.** `getfacl /dev/dri/renderD128` shows
`user:zarmeza:rw-`: udev already granted a per-user ACL, so the render nodes
were readable before `usermod` ran and would have been readable regardless.
The claim that missing group membership would silently degrade Vulkan to
llvmpipe was based on the `crw-rw---- root:render` mode bits alone, without
reading the ACL. It never applied on this system. The `usermod` did take
effect after re-login -- both groups are present now -- so it was harmless,
just unnecessary.

**The device is real and correctly identified:**

    Vulkan0: AMD Radeon RX Graphics (RADV POLARIS11) (4096 MiB)
    Vulkan1: Intel(R) HD Graphics 630 (KBL GT2) (11529 MiB)

Worth pinning down which is which before trusting any number: the Intel
integrated part reports 11.5 GiB and would look like the better target, but
it is the weak one. `--list-devices` settles it rather than a benchmark
number being interpreted hopefully.

**`-d` is not a valid flag; it is `-dev`.** Guessing at the short form printed
the help text instead of running. `llama-bench -dev Vulkan0` is what works.

**Build layout worth knowing:** `build-cpu/` and `build-vk/` are separate
trees. The CPU build is kept deliberately as the baseline, so re-benchmarking
either does not mean rebuilding both.

### 2026-10-08, writing the bot

Starting point, in the order that de-risks:

1. **A client for `llama-server`.** It speaks OpenAI's API
   (`POST /v1/chat/completions`, `tools/server/server.cpp:274`), so a plain
   `HTTParty.post` works — a library the project already depends on via
   `exercism`. No new gem. Config in `.env.sample` as `LLM_URL` / `LLM_MODEL`, so
   swapping models or pointing at a cloud endpoint later is config, not code.
2. **The message handler.** `@bot.message { |event| ... }` — `CommandBot` does
   not override `#message`, so non-prefixed messages reach registered handlers.
   Guard on `event.message.mentions?(bot_id)` and strip the mention from the
   prompt via `clean_content`.
3. **Streaming into one message.** ~7s for 200 tokens, so edit the message as
   tokens arrive rather than posting once at the end. This is the main
   divergence from the `scrappy` shape, where the reply is a single send.
4. **Per-channel history, 8-10 turns**, in memory only.
5. **Thread per conversation** — `start_thread_with_message` is available
   (`discordrb/api/channel.rb:484`) and `event.message.id` supplies the id.
6. **Concurrency guard.** Mutex plus "busy" reply; 28 t/s is not a number two
   simultaneous users should divide.
7. **Specs against a fake endpoint.** `instance_double` on HTTParty, never a real
   model in CI.

Write it behind a feature flag or a separate PR per step if it grows — the
first slice should stay small enough to review in one go.

#### Blocking the benchmark

None. Setup is mechanical; model size is already decided.

#### Blocking the implementation

- ~~**[need] Turn count for memory, and context window.**~~ **Resolved, and
  revised upward.** Prompt processing measures 173 t/s on GPU, not the 31 t/s
  the CPU baseline implied, so a 700-token four-turn history costs ~4s rather
  than ~22s. **The 4-6 cap was sized against the wrong number; 8-10 turns is
  now reasonable.** Context window is the same token budget and competes with
  history for it.
- ~~**Streaming.**~~ **Resolved: viable.** 28 t/s puts a 200-token reply at
  ~7 seconds, comfortably inside rate limits for one Discord message edit per
  token. Build it rather than leaving it deferred.
- **Persona wording.** The system prompt text itself is unwritten. Short, and
  it should say what the bot will not answer as much as what it will.
- **Safety, raised rather than decided.** This is a public university Discord
  server and the bot has no moderation hooks. A local model is unfiltered, an
  LLM will comply with very nearly anything asked, and history is in memory
  only -- so nothing is durable, but everything is live. Rate limiting and a
  per-user cap are worth considering before real traffic arrives.
- **Concurrency.** Default applied: mutex plus queue, "busy" reply while one
  generation is in flight. Parallel requests divide throughput at this speed.
- **Failure when `llama-server` is down.** Default applied: mirror `scrappy`
  -- readiness probe, bounded timeout, friendly message, `backtrace.txt`.
- **CI never touches a real model.** Specs target a fake endpoint via
  `instance_double`, following the `scrappy` and `exercism` patterns.
  `httparty` is already a dependency, so no new gems are needed.
