## Decisions

- **`init` did the wiring, not a hand-edited `AGENTS.md`.** Running
  `zanoria init` appended the block between `<!-- carrot-handoff:begin -->` and
  `<!-- carrot-handoff:end -->`. Everything the existing guide already said is
  untouched; the block sits after section 4.
- **The markers keep the old name, on purpose.** `zanoria init` matches on them
  to replace a block in place rather than append a second copy. Renaming them
  would mean every wired repository gained two sets of instructions — one saying
  `carrot-handoff`, one saying `zanoria` — with an agent reading both and nothing
  failing. They are format identifiers, not product names.
- **`.carrot.md` keeps its name for the same reason.** Renaming the file would
  hide every note already written: `status` would report `no handoff note` and
  `load` would fail while the file sat there unread. It is the one rename step
  that loses data.
- **The block already said `zanoria`.** The tool was renamed upstream and this
  file was re-inited afterwards, so the three command references were corrected
  by the tool rather than by hand — one marker pair, three lines changed,
  surrounding prose untouched. Worth confirming rather than assuming: it is the
  path that would otherwise have left a duplicate block here.


### 2026-10-08, local LLM chat

- **Benchmark before building.** No bot code until Vulkan is measured. Every
  design question below -- streaming vs one-shot, model size -- depends on
  whether this GPU does 25 tok/s or 12, and guessing costs a rewrite.
- **Model is Qwen2.5-3B-Instruct Q4_K_M (~2GB)**, with 1.5B downloaded
  alongside purely for comparison. 4GB VRAM is the real ceiling and 3B fits
  with room for KV cache.
- **`llama-server` runs on the host**, not in a container. The bot container
  cannot reach the host localhost; alternatives are a sibling compose service
  or `extra_hosts`. A sibling service is the most portable and matches how
  `browser` already works here, but needs a llama.cpp image with Vulkan and
  upstream ships no Dockerfile. Host is less work and easier to curl when
  debugging.
- **Docker networking, for the record** -- this is the part that is easy to get
  wrong: a container has its own network namespace, so `localhost` inside it is
  the container, not the machine. Three ways out: (1) sibling service in
  compose, reachable by service name, which is what `scrappy` already does
  with `browser`; (2) `extra_hosts: host.docker.internal` plus a host process;
  (3) `network_mode: host`, Linux only, so rejected as it breaks Mac and
  Windows.
- **`!chat` rather than mention-triggered**, pending the open questions below.
  The existing bot is strictly `-`-prefixed, one command per file, so a
  mention-triggered feature needs a message listener and is a structural change
  rather than one more file in `commands/`.


### 2026-10-08, chat design decided

- **Mention-triggered takes priority**, with `!chat` still supported
  afterwards if time allows. The instinct was to keep it prefix-only because
  that fits the existing architecture, but a Discord bot that ignores you
  unless you remember a bang is a worse experience, and dropping the prefix
  for now simplifies the first slice: no command file, no dynamic loader, no
  module-name camelization to fit through.
- **Memory is per-channel, in-memory, last N turns.** N is not fixed yet and
  should come out of the benchmark -- a larger context is more prompt to
  re-read per request, and at any plausible tok/s that cost is felt.
  Deliberately not persisted: that is a data-shape decision, not a feature.
- **One thread per conversation.** Context stays visible to everyone instead
  of scrolling away, at the cost of one extra Discord API call.
- **Spanish, TINAJA flavour, with a system prompt.** Chosen over raw
  completion because output quality moves more on this than model size does.
- **Casual-chat scope, for now.** Explicitly a starting position, not a
  judgement that hallucination is acceptable forever: 3B models invent
  confident nonsense on anything needing real knowledge, and this is an
  engineering community. Revisit if the chat ever becomes study help, at
  which point a refusal-flavoured system prompt is the cheap mitigation and
  retrieval is the real one.

### 2026-10-08, local LLM chat

**ROCm is installed and broken on this machine.** `rocminfo` reports
`HSA exception: Agent creation failed`. The card is Baffin/GCN4, which
predates ROCm supported range, so this is permanent, not a misconfiguration.
Do not spend time on it. RADV (Vulkan) is the working path.

**An earlier plan assumed CPU-only inference and was wrong.** The 12 tok/s
figure remembered from Windows was measured on the GPU, not the CPU. That
inverted the whole sizing analysis: a 7B partially offloaded plausibly
produced 12 tok/s, which means a fully-resident 3B should land meaningfully
faster. The CPU-only framing -- 4 cores, 8 threads, pick the smallest model
possible -- was retracted.

**Reading `/dev/dri/renderD128` will hang or fail, and Vulkan will silently
fall back to software.** The user is not in the `video` or `render` groups:

    id -Gn -> zarmeza adm cdrom sudo dip plugdev users lpadmin lxd docker
    /dev/dri/renderD128 -> crw-rw---- root:render

Worse than a failure is the fallback: llvmpipe (`lvp_icd`) is present, so
Vulkan appears to work while running *slower* than plain CPU. If benchmark
numbers come back implausibly bad, check group membership before anything else.

**Building the Vulkan backend needs packages that are not installed.**
`glslc` and `glslangValidator` are both absent, and so is `vulkan.h`
(`libvulkan-dev`). llama.cpp compiles its compute shaders at build time, so
`-DGGML_VULKAN=ON` fails on a clean install.

### 2026-10-08, local LLM chat

Setup, in this order. Steps 1 and 2 need sudo and are the user to run them:

1. `sudo usermod -aG video,render $USER` -- then **log out and back in**,
   since group membership is fixed at session start. Verify with `id -Gn`.
2. `sudo apt install libvulkan-dev glslc`
3. Build:
   `cmake -B build -DGGML_VULKAN=ON && cmake --build build --config Release -j`
4. Download `Qwen2.5-3B-Instruct-Q4_K_M.gguf` (~2GB) and the 1.5B for
   comparison. Only `ggml-vocab-*.gguf` tokenizer files exist locally; there
   are no model weights.
5. **Benchmark with `llama-bench`, Vulkan and CPU, both models.** This is the
   fork in the road:
   - ~25+ tok/s on Vulkan -> design for token streaming, 3B is comfortable
   - ~12 tok/s, GPU not actually engaged -> CPU-bound, design for one-shot
     replies and reconsider model size
6. Only then write the command.

The design questions under `Open questions` are deliberately unanswered. They
should be answered against the benchmark numbers, not against estimates.

### 2026-10-08, local LLM chat

#### Blocking the benchmark

None. Setup is mechanical; model size is already decided.

#### Blocking the implementation

- **[need] Turn count for memory, and context window.** Both should come out
  of the benchmark rather than a guess: every turn is re-read from prompt on
  every request, so at this speed the cost is visible. Likely small, 4-8.
- **Streaming.** Deferred until there is a number. Above ~25 tok/s, editing one
  message per token is within rate limits and worth doing.
- **Persona wording.** The system prompt text itself is unwritten. Short, and
  it should say what the bot will not answer as much as what it will.
- **Safety, raised rather than decided.** This is a public university Discord
  server and the bot has no moderation hooks. A local model is unfiltered, an
  LLM will comply with very nearly anything asked, and history is in memory
  only -- so nothing is durable, but everything is live. Rate limiting and a
  per-user cap are worth considering before real traffic arrives.
- **Concurrency.** Default applied: mutex plus queue, "busy" reply while one
  generation is in flight. Parallel requests divide throughput at this speed.
- **Failure when `llama-server` is down.** Default applied: mirror `scrappy`
  -- readiness probe, bounded timeout, friendly message, `backtrace.txt`.
- **CI never touches a real model.** Specs target a fake endpoint via
  `instance_double`, following the `scrappy` and `exercism` patterns.
  `httparty` is already a dependency, so no new gems are needed.
